## Must-verify on GPU (nothing here can run CPU-only)

1. **bf16 numerics (F1).** The assert fires or passes on an L4; every loss in
   the 30-step gate is finite, `n_nonfinite == 0`, `s_min` and `max_abs_logit`
   stay in sane ranges (log them every step). Watch for k3 `exp(r−s)` overflow
   in degenerate rows — the tripwire aborts (exit 3) rather than corrupting.
2. **F3 dynamics.** **D4 (round 2): the earlier "2-3× walltime drop" prediction
   is WRONG and retracted.** Pilot 351229 measured `train_step_wall_s` ≈ **52-65
   s/step at every chunk size** (log lines 844, 881, 918, 955): the step is bound
   by the forward/backward passes (still 288 fwd+bwd + 288 reference forwards),
   not by the AdamW step, and the new rollout-time scoring forward adds time. The
   correct expectation per step: ~52-65 s, no 2-3× drop. Watch `train_log
   grad_norm`/`loss_pg`/`policy_push` move like one update per step. Re-pick the
   lr grid — AdamW steps per training step fell 288→1, so the old lr values are a
   moved target (audit §4).
3. **F4 stability.** **B4 (round 2): "loss_pg ≢ 0" is REMOVED — it is
   unevaluable by construction** (with ratio ≡ 1, row_pg = a_r and the logged
   mean = −mean(advantages) ≡ 0 under group normalization; measured 1.1e-18 at
   G=8, H=36). The criterion is now: `grad_norm` **finite and > 0 every step**,
   and `lora_norm` **changes between steps**. `loss_kl ≥ 0` on record 1 (k3);
   the detached `policy_push` diagnostic (`-(a·seq_logp).mean()`, logged per
   step) makes the policy push measurable — expect it to deviate from ~0 as the
   policy moves; `entropy_first > 0` throughout; no collapse to a single order
   (`n_unique_orders > 1` every step); with ratio ≡ 1 the clip is a dormant
   guard — verify the k3 term is doing the trust-region work. D6 adds
   `max_abs_logratio`/`clip_frac` per step: with ratio ≡ 1 they sit at 0/0%, and
   on GPU they measure the bf16 noise floor between the rollout-chunk forward
   and the micro-batch forward (F4a).
4. **F5 resume.** Resubmitting `--resume` prints "resume drill: adapter … N
   trainable params" with N > 0 and " + optimizer" when `optimizer.pt` exists;
   the run continues at `state.step + 1` with finite loss. **D8 (round 2):**
   `--lr` is NOT a resume knob — `load_state_dict` restores the SAVED optimizer
   lr into `param_groups`; if the CLI `--lr` differs, main() prints a WARNING
   ("the SAVED value wins on resume … use a fresh --out for a different-lr
   arm"). Expect and read the warning; changing lr between resubmissions is a
   mislabeled run.
5. **F8/F9.** Zero "right-padding was detected" warnings in the log; sample-row
   `ids` (rec["samples"]) score to the same text row they came from.
6. **F10 + F11 drill.** **B3 (round 2): the drill command is `scancel --batch
   --signal=TERM <jobid>`** — without `--batch`, Slurm does NOT signal the batch
   shell ("By default, signals other than SIGKILL are not sent to the batch
   step"; the man page's `-b/--batch` or `-f/--full` flags exist precisely for
   this). This pairs with `#SBATCH --signal=B:TERM@600` in gpu-pilot.sbatch: the
   shell trap forwards the signal to python → `checkpoint-<step>/` with both
   adapter and optimizer, `state.json` written last, `"event":"sigterm"` in
   train_log.jsonl; resubmit resumes `state.step + 1`, optimizer loaded, finite
   loss. F13: no checkpoint is ever written with a NaN (a deliberately poisoned
   step aborts at save time).
7. **F17.** With a constant policy the advantage columns should sit ~0 (no
   demand-luck signal); with a real policy the signal is policy-sample driven.

## How to run the pilot (the audit's 30-step gate)

Entry points: `hpc-umbrella/config.sh` (the pins file) and
`hpc-umbrella/gpu-pilot.sbatch` (+ `stage.sh` for staging).

**B1 — stage from the HOME CLONE, never the scratch kit.** When `KIT_DIR` is
already the scratch kit, `stage.sh:43-49` SKIPS the rsync and re-execs the stale
copy — the old `stage.sh` (swallows pull failures) and the old
`gpu-pilot.sbatch` (no wait loop, no hard gate) get submitted. The documented
flow is: update + run from the home clone (`OPERATOR.md:34-39,78`).

**B2 — commit first, then set EXPECTED_COMMIT to the NEW HEAD.** The fixes exist
only in this working tree; the cluster checks out GitHub `master`. The gate must
pin the **fixes commit**, NOT `51d3d5a` (that is the pre-fix HEAD — followed
literally it passes the pre-fix code, the exact F6 failure mode). The full
40-char SHA is required (`rev-parse HEAD` comparison; a short SHA always fails).

**Prerequisite: the operator commits AND pushes this working tree, then on the
login node:**


## Known gaps (no code; disclosed so the gate is not misread)

- **F2 nuance:** `pad_token` == EOS id **151643** for Qwen3-0.6B, so a sampled
  `<|endoftext|>` stop token is STRIPPED at `rollout` (`grpo_train.py:270`) and
  never scored, while `<|im_end|>` stops are kept. In the verify probe 0/16 rows
  hit this (all ran to 8 tokens); it only matters for degenerate completions.
- **F1 nuance:** a NaN that first appears INSIDE `generate()` (finite weights,
  overflowing logits) still exits 1 with no `checkpoint-prenan/` — the tripwire
  only sees post-generate loss/grads. bf16 makes this unlikely (the abort was
  measured on an fp16 divergence); if it happens the run restarts from the last
  checkpoint, it does not corrupt weights.
- **D1 (cpu-harness):** the sbatch stub is migrated to the F2 triple contract —
  the OPERATOR step-3 harness (batched rollouts + checkpoint/resume on the CPU
  node) is the first job that proves it end-to-end on the cluster.
