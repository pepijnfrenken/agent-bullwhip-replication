## Verdict: NOT READY (as written)

On every point a CPU-only box can check, the Python changes are faithful to the audit. The blockers are in the deploy procedure and the gate definition. Run the FIXES runbook verbatim and the cluster runs the **pre-fix code** with the **old sbatch**; the TERM drill sends no signal; and one of the five pass criteria is unevaluable by construction. All four blockers can be fixed without touching Python (B1–B4 below). Once they are fixed, the gate is runnable.

## 3. Blockers

**B1. The runbook stages a stale kit.**
- FIXES:85-86 runs `cd /scratch-shared/$USER/bullwhip/kit && bash stage.sh`.
- When KIT_DIR is already the scratch kit, `stage.sh:43-49` skips the rsync and re-exec. The scratch kit is the copy from the previous staging, so the **old** `../../hpc-umbrella/stage.sh` runs (it swallows pull failures) and the **old** `gpu-pilot.sbatch` is submitted (no F10 wait loop, no F6 stamp). The documented flow is to update and run from the home clone (`OPERATOR.md:34-39,78`).
- Fix: `cd ~/bullwhip-repo && git pull --ff-only && cd hpc-umbrella && EXPECTED_COMMIT=<sha> bash stage.sh`. Make the gate edits in the scratch kit **afterwards**, because `rsync --delete` overwrites them.

**B2. Nothing is committed, and FIXES gives the wrong `EXPECTED_COMMIT`.**
- The cluster checks out GitHub `master` (`stage.sh:59-60`), but the fixes exist only in this working tree.
- FIXES:81 says "set it to the **audited commit's** SHA". The audited commit is `51d3d5a` (AUDIT:7), the pre-fix HEAD. Followed literally, the gate passes the pre-fix code: the exact F6 failure mode.
- Fix:
  1. Commit and push.
  2. Set `EXPECTED_COMMIT` to the full 40-character SHA of the **fixes** commit. The gate compares against `rev-parse HEAD`, so a short SHA always fails.
  3. Confirm `repo HEAD=<that sha>` in the pilot log.

**B3. The TERM drill command sends no signal.**
- `scancel --signal=TERM <jobid>` does not signal the batch step. The Slurm `scancel` man page says: "By default, signals other than SIGKILL are not sent to the batch step (the shell script)". It takes `-b/--batch` or `-f/--full` (https://slurm.schedmd.com/scancel.html).
- Python is a direct child of the batch shell (`gpu-pilot.sbatch:68`, no `srun`), so nothing receives TERM and the job runs on to step 30. Because step C saves every step, `checkpoint-*` dirs exist anyway; only the missing `"event":"sigterm"` record would reveal that the drill did nothing.
- Fix: `scancel --batch --signal=TERM <jobid>`. This matches `#SBATCH --signal=B:TERM@600` (`gpu-pilot.sbatch:25`), and the shell trap forwards the signal to python.

**B4. The pass criterion "loss_pg is not ≡0" can no longer be evaluated.**
- With ratio = 1, `row_pg = a_r` (`grpo_train.py:468-470`). The logged value is the mean over micro-batches (`:516,544`), which equals −mean(advantages), and `group_normalize` makes that zero.
- Measured: **1.1e-18** at G=8, H=36 (`/tmp/bwverify/losspg.py`).
- The gradient is not zero; the logged value is. On GPU any nonzero `loss_pg` will be bf16 ratio noise. As written, the criterion either fails a healthy run or passes on noise, and FIXES must-verify #3 repeats it.
- Fix (runbook only): require `grad_norm` to be finite and > 0 every step, and `lora_norm` to change between steps. If a "policy-push" number is wanted, add a detached `-(a*seq_logp).mean()` diagnostic.

## 5. Residual GPU-only risks

- **bf16 numerics.** Losses should stay finite. k3 `exp(r−s)` overflows only if r−s > ~88, and the tripwire would catch that with exit 3.
- **Ratio noise between the rollout-chunk forward and the micro-batch forward.** Unmeasured (F4a).
- **`PeftModel.from_pretrained(..., is_trainable=True)`, then optimizer `load_state_dict` on CUDA.** Never executed anywhere. My CPU attempt was killed (see below).
- **Transient memory in `_old_logprobs`.** It materializes full-vocab `log_softmax` over the whole chunk (`:330-333`, `:310`). Prompts are 190-228 tokens (`/tmp/bwverify/plen.py`), so this is about 2.3 GB of bf16 at `rollout_batch=16`, which fits an L4 (the old pilot peaked at about 6 GB). At `rollout_batch<=0` with G=16 it would be about 9 GB. The same allocation in fp32 on this box is what pushed my CPU probe to ~8.4 GB RSS and the OOM kill.
- **Walltime.** From 351229: steps A+B take about 19 min, and step C ran ~92 s/step before the extra scoring forward. 30 steps should take about 50-55 min, a total of about 75 min against TERM at 1 h 50. That fits, and each resubmission re-runs A+B (~19 min). [INFERENCE] Post-fix per-step time is not measured.
- **Generation-time NaN.** Not caught by the tripwire: exit 1 with no prenan checkpoint.
